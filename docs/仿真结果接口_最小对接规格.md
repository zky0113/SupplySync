# 旧版仿真接口草案（历史资料，非当前实现说明）

> 当前工作台直接使用固定并经审计的本地 Python 计算副本，不依赖此处拟议的 HTTP 接口。此文档保留供未来服务化参考，其中“尚未接入”等表述已过时；请以 `README.md` 与当前源码为准。

本文件是前后端**工程约定**，不是赛事官方规定，也不表示接口已经实现。当前前端只读取已校验的合成输入；预测、补货、仿真和 Agent 仍保持禁用。队友当前 `server.py` 只有 `/health`、`/scenarios`、`/experiment`，其中 `/experiment` 尚缺共同初态、逐日账本和验证状态，**不可直接作为本页面的正式效果数据源**。

## 对接顺序

1. 后端先修复零发货欠单、S1 零订单日和预热/测量时钟，并通过守恒及同初态回归测试。
2. 只接入**一个**已验证的场景及 S1/S2 对照；前端先显示指标与数据来源，再接逐日曲线。第二个场景选压力场景，如实展示改善或变差。
3. 预测、事前计划和 Agent 各自通过验收后再开放相应操作；绝不以旧报告数值或示意数值填充空白区。

## 最小请求与响应

推荐把现有算法封装成 `POST /api/v1/paired-experiment`，一次仅计算一个场景。后端可以先同步返回；若超过前端可接受的等待时间，再改为 `202 + run_id` 和结果查询，不改变结果字段。

```json
{
  "schema_version": "1.0",
  "snapshot_id": "e697ed76be457e7f",
  "scenario_id": "baseline",
  "horizon_days": 30,
  "policy_ids": ["S1", "S2"],
  "comparison_mode": "paired_common_initial_state"
}
```

`snapshot_id` 必须等于本页输入快照；`scenario_id` 必须来自本页六场景配置；`horizon_days` 为正整数，不能悄悄改为其他天数。`comparison_mode` 表示两策略具有相同的初始库存、在途、欠单、外部需求及扰动序列。若算法采用稳态预热，请新增明确的预热定义和计费范围，不能仍声称“同初态干预”。

建议响应字段如下。示例中的 `…` 是字段说明占位，**不是可展示的模拟结果**。

```text
schema_version: "1.0"
run_id: 后端生成的不可复用运行标识
status: "validated" | "failed"
manifest:
  snapshot_id, scenario_id, horizon_days, policy_ids
  code_version, seed, measurement_start, measurement_end
  warmup_rule, initial_state_hash, exogenous_input_hash, cost_config_hash
  validation_checks: 每项 {name, passed, details}
metrics: 两行，每行含
  policy_id, total_cost, cost_breakdown
  terminal_demand_units, terminal_sales_units, lost_sales_units
  stockout_rate, average_system_inventory_units, turnover_window
  inventory_scope, bullwhip_by_tier
daily: 每策略每天一行（可在首版仅提供总量），每行含
  policy_id, date, demand_units, sales_units, lost_sales_units
  closing_on_hand_units, open_purchase_order_units, in_transit_units
  backorders_owed_units, daily_cost, daily_cost_breakdown
error: status=failed 时提供 {code, message}，不得返回貌似成功的空数值
```

金额统一为人民币元，数量统一为件，`stockout_rate` 统一用 0–1 小数。前端把两策略差值展示为**百分点**，周转次数需明确测量窗口与库存范围。`cost_breakdown` 的各项之和必须等于 `total_cost`；`sales_units + lost_sales_units = demand_units`；逐日记录、总指标和图表必须能互相复算。采购成本仅在外部采购进入供应链时计费，内部转运不能重复采购计费。

## 前端验收门槛

收到结果后，前端先检查以下条件，全部通过才显示效果数字；否则保留当前 `—` 和“待验证”状态，并给出错误原因：

- `status=validated` 且所有 `validation_checks.passed=true`；`snapshot_id` 与当前展示快照一致。
- 恰好一条 S1、一条 S2 指标；两者场景、窗口、初态哈希、外生输入哈希和成本哈希一致。
- 非负需求、销量、失销、库存、订单、成本；缺货率在 `[0,1]`，各项指标为有限数；零分母显示 `N/A`。
- 每个策略的逐日日期完整且不重复；每日需求与失销/销量守恒；总指标与逐日求和一致。
- 图、表和 Agent 引用同一个 `run_id`；更改节点或标签不重新运行；新运行失败不能覆盖上一次成功结果。

这只是**前端防误展示**，不能代替后端仿真单测与独立复算。不要为了通过校验而在前端修补后端数据。

## 预测、计划与 Agent 的后续字段

后续端点可沿用 `docs/接入合同.md` 的 `ForecastRecord`、`PlanLine`、`NodeState`、`AgentResult`。预测请求必须含 `cutoff`，只返回截至该日期可知的数据；计划应同时返回请求量、分配量、期望到货日、约束原因，不能把事后发货日志充作事前建议。Agent 的数值解释必须附 `run_id`、实际工具轨迹和证据引用，失败时返回明确错误，不编造工具结果。

场景配置在当前页面的“实验设计者预览”中可见；后端策略只应得到决策日已知日历与截至该日状态，不得读取未来真值或未发生的扰动。正式公开部署时，密钥只放服务端环境变量，不进入仓库、浏览器、CSV 或下载报告。
